LIMIT / OFFSET

For

  • Jumps straight to any page: page 500 is one query, no state.
  • Works with any ORDER BY, including one the user picks at run time.
  • A total page count is the same count(*) you already wanted.
  • Trivial to write, and every framework generates it for you.

Against

  • Cost grows with depth: the server reads every skipped row and discards it.
  • Rows repeat or vanish when the data changes between two page requests.
  • The deepest pages are the slowest, and nobody notices in testing because testing looks at page one.

Keyset

For

  • Constant cost at any depth: the index is asked where to start.
  • Stable while the data moves - a page is defined by the last row you saw, not by how many rows are in front of it.
  • Reads exactly the page size, so the buffer count stops being a function of how far in the user has gone.

Against

  • No jumping. You can go next and previous, not to page 500.
  • Needs a total order: the sort column plus something unique to break ties.
  • Every sort the user can choose needs its own index and its own cursor.
  • Row comparison wants one direction - mixed ASC/DESC needs writing out by hand, and NULLs in the sort column will silently skip rows.
  • The cursor is state the client has to carry.
